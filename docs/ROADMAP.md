## Phase 1: 프로젝트 골격 (1-2일)

### 작업 항목

- Next.js 프로젝트 구조 설정
  - 기존 스타터의 `src/app`, `src/components`, `src/lib` 구조를 블로그에 맞게 정리
  - 스타터 예제 페이지(`login`, `signup`, 랜딩 섹션)의 제거 여부 결정 (PRD 8장 열린 질문)
- Notion API 연동 환경 구축
  - `@notionhq/client` 설치
  - `.env.local`에 `NOTION_API_KEY`, `NOTION_DATABASE_ID` 설정, `.env.example` 작성
  - `.gitignore`에 `.env*.local`이 포함되어 있는지 확인
  - Notion Integration 생성 및 데이터베이스 연결 (PRD 7장 2단계)
- 기본 레이아웃 구조 생성
  - 루트 레이아웃에 헤더, 메인, 푸터 배치
  - 기존 `main-nav`, `mobile-nav`, `theme-toggle` 연결 확인

### 왜 이 순서인가?

가장 먼저 골격을 세우는 이유는 이후 모든 작업이 이 위에서 이루어지기 때문이다. 환경 변수와 Notion 연결이 먼저 확인되어야 이후 단계에서 데이터 문제와 설정 문제를 구분할 수 있다. 다음 단계인 공통 모듈이 Notion 조회를 바로 호출할 수 있도록 연결 상태를 여기서 확정한다.

### 완료 기준

- [ ] `npm install` 후 `npm run dev`로 개발 서버가 실행된다.
- [ ] `.env.example`만 저장소에 있고, 실제 키는 커밋되지 않는다.
- [ ] 서버 코드에서 Notion 데이터베이스 조회가 성공한다(응답 로그 또는 임시 확인 코드로 검증 후 제거).
- [ ] 루트 레이아웃에서 헤더와 푸터가 모든 페이지에 보인다.
- [ ] `npm run check-all`과 `npm run build`가 통과한다.

## Phase 2: 공통 모듈 (2-3일)

### 작업 항목

- 공통 타입 정의 (`src/lib/notion/types.ts` 등)
  - `Post`: id, slug, title, category, tags, publishedAt, status
  - `Category`: 카테고리 이름 목록 (PRD 3장 속성 기준)
- Notion API 공통 함수 (`src/lib/notion/`)
  - `fetchPages()`: `Status = 발행됨`인 행을 `Published` 내림차순으로 조회 (PRD 3.1, 4.1)
  - `fetchPageContent(pageId)`: 페이지 본문 블록을 조회하고, 하위 블록이 있으면 재귀적으로 가져온다.
  - Notion 응답을 `Post`로 변환하는 매퍼 함수
  - 조회 실패 시 에러 처리 방식 정의
- 공통 컴포넌트
  - `Header`, `Footer`: 기존 `src/components/layout/`를 블로그 내비게이션에 맞게 수정
  - `Card`: 글 목록의 항목 카드 (제목, 카테고리, 태그, 발행일 표시)

### 왜 이 순서인가?

목록, 상세, 카테고리, 검색은 모두 같은 데이터 조회 함수와 타입을 사용한다. 기능보다 먼저 공통 모듈을 만들어야 페이지마다 같은 코드를 중복해서 작성하지 않는다. 특히 `fetchPages()`와 `Post` 타입은 핵심 기능의 목록과 상세 페이지가 바로 쓰므로 3단계 전에 끝나 있어야 한다.

### 완료 기준

- [ ] `fetchPages()`가 `초안` 행을 결과에서 제외한다.
- [ ] `fetchPages()` 결과가 `Published` 내림차순으로 정렬된다.
- [ ] `fetchPageContent()`가 문단, 제목, 목록, 코드, 이미지, 인용, 구분선 블록을 모두 가져온다.
- [ ] `Post` 타입과 매퍼로 Notion 속성이 누락되어도(예: `Tags` 비어 있음) 에러 없이 처리된다.
- [ ] `Card`, `Header`, `Footer`가 props만으로 동작하며, Notion 호출을 직접 하지 않는다.
- [ ] `npm run check-all` 통과.

## Phase 3: 핵심 기능 (3-4일)

### 작업 항목

- 블로그 글 목록 페이지 (`/`) — PRD 4.2
  - 서버 컴포넌트에서 `fetchPages()` 호출
  - 발행된 글을 `Card` 목록으로 표시
  - 글이 없을 때 빈 상태 메시지
- 블로그 글 상세 페이지 (`/posts/[slug]`) — PRD 4.3
  - `slug`로 글 조회, 없거나 `초안`이면 `notFound()` 호출
  - 제목, 카테고리, 태그, 발행일 표시
  - `generateStaticParams`와 `generateMetadata` 적용 여부 결정
- Notion 콘텐츠 렌더링 — PRD 4.3
  - 블록 타입별 렌더러 작성 (문단, 제목 1~3, 글머리/번호 목록, 코드, 이미지, 인용, 구분선)
  - 굵게, 기울임, 링크, 인라인 코드 등 rich text 주석 처리
  - 알 수 없는 블록 타입은 무시하지 말고 빈 영역으로 처리해 에러가 나지 않게 한다.

### 왜 이 순서인가?

블로그가 블로그로서 동작하는 데 가장 중요한 기능이다. 이 단계가 끝나야 실제 Notion 글이 사이트에 나타나므로, 부가 기능보다 먼저 완성한다. 목록과 상세가 완성되어야 4단계의 카테고리와 검색이 그 목록을 필터링하는 방식으로 붙을 수 있다.

### 완료 기준

- [ ] 홈에서 `발행됨` 글이 발행일 순서대로 보인다.
- [ ] 목록 항목을 누르면 상세 페이지로 이동하고, 제목과 본문이 Notion과 같은 내용으로 보인다.
- [ ] `초안` 글의 상세 URL이 404를 반환한다.
- [ ] 없는 `slug`가 404를 반환한다.
- [ ] 지원 대상 블록 타입 전체를 샘플 글로 확인했다.
- [ ] 모바일 너비와 데스크톱 너비에서 상세 페이지 본문이 읽기 쉽다(본문 너비 제한 적용).

## Phase 4: 추가 기능 (2-3일)

### 작업 항목

- 카테고리 필터링 — PRD 4.4
  - `/categories/[category]` 페이지 구현
  - `Category` 옵션 목록을 헤더 또는 홈에서 링크로 제공
  - 카테고리에 글이 없을 때 처리
- 검색 기능 — PRD 4.5
  - 제목과 태그 기준 검색
  - 검색 방식 결정: 글 수가 적으면 클라이언트 필터링, 늘어나면 서버 조회 (PRD 8장 열린 질문)
  - 검색 결과가 없을 때 빈 상태 메시지
- SEO 최적화
  - 페이지별 `title`, `description` 메타 태그 (`generateMetadata`)
  - Open Graph 기본값 설정
  - `sitemap.xml`, `robots.txt` 추가 (PRD 범위 밖이었으나 SEO 목적에 포함)

### 왜 이 순서인가?

블로그 동작에 필수는 아니지만 사용성과 검색 노출을 높이는 기능이다. 핵심 기능이 완성된 뒤 추가해야 목록과 상세 로직을 다시 고치는 일을 줄일 수 있다. SEO는 상세 페이지가 완성되어야 페이지별 메타 정보를 설정할 수 있으므로 이 단계에 둔다.

### 완료 기준

- [ ] 카테고리 링크를 누르면 해당 카테고리 글만 보인다.
- [ ] 제목 또는 태그에 검색어가 포함된 글만 보인다.
- [ ] 검색 결과가 없으면 빈 상태 메시지가 보인다.
- [ ] 상세 페이지의 `<title>`과 `<meta name="description">`이 글 내용을 반영한다.
- [ ] `/sitemap.xml`과 `/robots.txt`가 응답한다.
- [ ] `npm run check-all` 통과.

## Phase 5: 최적화 및 배포 (1-2일)

### 작업 항목

- 성능 최적화 — PRD 6장
  - Notion API 호출 횟수 확인, 캐싱 주기 결정 (`revalidate` 또는 ISR, PRD 8장 열린 질문)
  - 이미지 처리 방식 결정: Notion 이미지 URL 만료 대응 (PRD 8장 열린 질문)
  - `next/image` 적용 가능한 곳에 적용
- 반응형 디자인 개선 — PRD 4.6
  - 모바일, 태블릿, 데스크톱에서 전 페이지 확인
  - 본문 가독성(줄 간격, 본문 너비) 조정
  - 다크 모드 지원 범위 확정 (PRD 8장 열린 질문)
- Vercel 배포
  - Vercel 프로젝트 연결
  - 환경 변수(`NOTION_API_KEY`, `NOTION_DATABASE_ID`) 설정
  - 프로덕션 빌드 확인 및 배포 URL에서 동작 확인

### 왜 이 순서인가?

기능이 확정되어야 어디가 느린지, 어떤 캐시 주기가 필요한지 알 수 있다. 기능이 바뀌는 중에 최적화하면 같은 작업을 반복하게 된다. 배포는 마지막에 하되, Vercel에 쓸 환경 변수는 Phase 1에서 이미 검증해 두었으므로 이 단계에서는 연결만 하면 된다.

### 완료 기준

- [ ] Vercel 프로덕션 URL에서 목록, 상세, 카테고리, 검색이 동작한다.
- [ ] Notion에서 글을 `발행됨`으로 바꾼 뒤 캐시 주기가 지나면 사이트에 반영된다(PRD 9장 성공 기준).
- [ ] 초안 글은 배포 환경에서도 노출되지 않는다.
- [ ] 모바일과 데스크톱에서 레이아웃이 깨지지 않는다.
- [ ] `npm run check-all`과 `npm run build` 통과.

- [ ] 초안 글은 어떤 경로로도 노출되지 않는다.
- [ ] 모바일과 데스크톱에서 목록, 상세, 카테고리, 검색이 정상 동작한다.
- [ ] `npm run check-all`과 `npm run build`가 통과한다.
